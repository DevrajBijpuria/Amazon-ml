## 4. Setup and interpretations

- **Baseline.** The rollback baseline is the immutable Phase 2.5 run in `phase2/output/phase2_5/frozen_50000/`: 50,000 training Source-1 entities against the full training Source 2 and Source 3, 11 blocking rules, cut-off 100, cap 100, HistGradientBoosting on F3 (42 features), threshold 0.8, 10,000 validation entities. Phase 3 only reads it.
- **P3-A rule set.** The frozen configuration (`phase2/config/phase2_5_frozen.yaml`) already contains B0's 8 rules plus house_locality, state_locality and address_signature. P3-A is that exact rule set plus postal_locality, so P3-A equals B0 plus the four locality rules the specification names, and it differs from the frozen baseline by postal_locality alone. The rules come from the frozen configuration, not from the example YAML in section 18 of the specification.
- **The phonetic question.** The frozen configuration has a phonetic rule (`name_phonetic`, B0). It keys one consonant skeleton of the whole compact core name. P3-D's `name_phonetic_token` keys each of the two rarest per-token consonant skeletons, and it is a separate function in `phase2/src/candidate_generation.py` with its own switch. Example (from a test): 'Acme Traders' gives `india|kmtrdrs` under name_phonetic and `india|pt|trdrs` under name_phonetic_token. Because the two rules are different, P3-D was run as specified: P3-A plus name_phonetic_token, with name_phonetic kept.
- **Keeping HGB frozen.** Every experiment uses the same hyperparameters (max_iter 200, random_state 42, early_stopping false), the same F3 features, the same sampling (negative ratio 5, hard-negative fraction 0.5 by name and address character-3-gram Jaccard) and the same entity-level validation split (20%, seed 42). HGB is retrained on each experiment's own training candidates, and the threshold is re-selected on validation macro F0.5 per entity (grid 0.05 to 0.95, ties go to the higher threshold). All of this runs through the unchanged Phase 2 function `run_phase2.train_stage`, the same code that produced the frozen baseline. The only feature that depends on blocking is `number_of_blocks_that_retrieved_pair`, and its definition is unchanged.
- **Candidate priority.** B0 defines one priority (`candidate_generation._cap`), and every experiment uses it unchanged. Within each Source-1 entity and target source, pairs are ordered by the number of rules that retrieved them (descending), then by the larger of the name-key and normalized-address edit similarities (descending), then by the target's position in its source file (ascending). The first `max_candidates_per_source1` are kept, and groups at or under the cap are kept whole. The priority uses no labels and no model scores, and the position tie-break makes the order total.
- **Scales.** Smoke runs use 1,000, diagnostic runs 10,000 and principal runs 50,000 training Source-1 entities. All of them use the full training Source 2 (5,034,616 records) and Source 3 (5,285,603 records), and all draw a deterministic seed-42 sample, which is the same 50,000 sample as the frozen baseline. Validation is 20% of each sample, so 200, 2,000 and 10,000 entities. The 50k validation entities are identical to the frozen baseline's, and the metric code checks this before every paired comparison.
- **Comparison baseline.** At 50k, experiments are compared with the frozen_50000 artifacts themselves. At 1k and 10k no frozen artifacts exist, so the frozen configuration was run through the Phase 3 runner at the same scale (`p3_frozen_baseline`). At 50k the same reference run checks the harness: it has to reproduce frozen_50000 exactly. Differences in macro F0.5 are judged with the Phase 2.5 paired entity bootstrap (B = 1000, seed 42).
- **Test data.** No experiment reads test data. Each run writes `matching_results.tsv` and `candidate_pairs.tsv` for its validation entities. The candidate file holds exactly the scored pairs, and the matches are the pairs scoring at or above the selected threshold. The unchanged challenge validator then checks these files with `--check-ids`, with the train Source 2 and Source 3 files standing in for the test ones.
- **Execution environment.** Every run in this report ran on the local workstation (Windows 11, 16 logical CPUs, 15.8 GB RAM, 6 worker processes), not on EC2. The specification describes AWS execution, but provisioning EC2 or S3 costs money and needs your approval, which has not been given, so none was used. Memory and runtime were measured the same way on this machine for every experiment, and the phase2 memwatch method runs in-process (`phase3/src/aws_runtime.py`).
- **Dependencies.** The same set as Phase 2.5, pinned in `phase3/requirements.txt`: pandas, numpy, scipy, scikit-learn, rapidfuzz, joblib, PyYAML, boto3 and pytest. Nothing was added.
- **Git commit.** The local git repository is rooted at the home folder and has no commits, so each manifest records a `code_sha256` instead: one SHA-256 over every source file in phase1/src, phase2/src and phase3/src.
